# VIO campaign: what it is for, how it works, what it found

`tests/vio_campaign.py` (`./bisg vio bench` / `./bisg vio check`) is the repeatable experiment behind the GPS-denied default. It
flies the same benchmark profile many times on fresh sims, under the shipped PX4 parameters and under ablations of them, compares
each flight against ground truth, and gives a PASS/FAIL verdict on one question: **is the ZED VIO pipeline calibrated on this
machine?** [vio.md](vio.md) explains the error sources and the calibration; this page covers the campaign itself and the results
of every campaign run so far (2026-10-15 to 2026-10-18, Workstation A).

All results are in JSON for plotting:

| file | contents |
|---|---|
| [`docs/data/vio_campaigns.json`](data/vio_campaigns.json) (590 kB) | all 12 campaigns: setup, verdict, per-config statistics, ablation deltas, pipeline calibration, reliability, every flight's metrics and events, a `history` table, metric definitions |
| [`docs/data/vio_campaigns_series.json`](data/vio_campaigns_series.json) (1.5 MB) | per flight, the 5 Hz error-over-time series (EKF2 and ZED horizontal error, EKF2 height error, ZED yaw error) |

Both are generated by `tests/vio_export.py` from the campaign directories (stdlib only; it uses `vio_report.py`'s metric getters and
statistics, so its numbers match each campaign's `summary.md`):
```
python3 tests/vio_export.py $ARCHIVE_DIR/vio_bench/*/ --out docs/data/vio_campaigns.json
```

## 1. Purpose

The sim default is GPS-denied like the real drone (`docker/sim/sim.yaml` `px4_params: [raptor]`): EKF2 gets
horizontal position, 3D velocity and yaw from the ZED Mini (real ZED SDK on the Isaac twin), height from baro + LW20, and horizontal
velocity also from the PMW3901 optical flow. Without GPS and magnetometer, the ZED is EKF2's only absolute horizontal and heading
reference, so EKF2's horizontal error is, to first order, the ZED's error. Whether that chain is right depends on things a single
test flight cannot separate:

- **Pipeline calibration**: the timestamp correction of the ZED odometry (zed.yaml sim `restamp_latency_ms`, which scales with
  the machine's real-time factor), the velocity frame and scale, the camera lever arm (`EKF2_EV_POS_*`).
- **PX4 parameters** chosen on 2026-10-15: `MC_YAWRATE_MAX 60` (fast yaw makes the IMU-less sim SDK slip its yaw),
  `EKF2_EVA_NOISE 0.01` (PX4 v1.17 floors the EV yaw variance at this value, so the default 0.1 means 18 deg and EKF2's heading lags the
  ZED), `EKF2_OF_QMIN_GND 1` (no flow fusion of quality-0 samples on the ground).
- **Random SDK tracking events** of the sim ZED (it runs without its IMU): yaw or position slips at frame gaps, pose jumps, yaw slips
  in rotations. They come and go between sim runs and no parameter removes them.

The campaign answers three questions, each with its own output:

| question | answered by | used for |
|---|---|---|
| Is the pipeline calibrated on this PC? | **verdict** (gated): latency, velocity scale, lever arm, event-free `calibrated` error | `./bisg vio check` after an EKF2/ZED-calibration change or on a new machine (CLAUDE.md gate) |
| What does each calibration buy? | **ablation**: each config vs `calibrated`, all flights and event-free flights | keeping or dropping a PX4 parameter |
| How often does the sim ZED fail, and why? | **failure attribution**: dominant SDK event per flight, frame gaps, pose jumps | separating parameter effects from SDK noise; deciding what to test on hardware |

It also yields concrete corrections: when the residual latency is off, the report prints the new `restamp_latency_ms`.

## 2. How a campaign runs

```
tests/vio_bench.yaml ──► vio_campaign.py ─┬─ for rep in 1..reps:  for config in configs:        (interleaved)
                                          │     ./bisg down; ./bisg all headless                 fresh sim (B18)
                                          │     wait zed-bridge "odometry ok"                     else Infra -> retry
                                          │     param set ... ; param show ... (read back)        else Infra
                                          │     wait EKF2 cs_ev_vel + cs_ev_yaw                   never fly without VIO
                                          │     tests/vio_bench.py in bisg-ros (OFFBOARD)         the flight
                                          │     docker cp flight.ulg ; tests/vio_eval.py          per-flight metrics
                                          └─ tests/vio_report.py ─► summary.md/json/csv, figures/*.svg, verdict (exit 0 = PASS)
```

Design choices and why:

- **Fresh sim per flight.** The ZED SDK connects once per sim run (B18) and its tracking errors (a tilted world frame, a slipped yaw)
  persist for the rest of that run, so flights in one sim would not be independent.
- **Interleaved order** (rep 1 of every config, then rep 2, ...): slow changes of the machine (thermal, cache, other load) do not line up
  with one config.
- **Infra failures are not VIO failures.** A wrapper that never connects, crashes (R9), or EV that EKF2 never fuses raises `Infra`: the
  attempt is logged and retried on a fresh sim (`max_attempts: 3`), and reported under reliability, not counted in the results.
- **Params set live and read back** on top of the scenario's param files; a value PX4 does not show back is an infra failure.
- **VIO fused before takeoff.** At rest PX4 fuses a fake position, so "ready for takeoff" does not mean the ZED is in
  ([vio.md](vio.md#arming-without-vio-safety-open)); the campaign waits for `cs_ev_vel` and `cs_ev_yaw` in `estimator_status_flags`.
- **Ground truth on PX4's clock.** Pegasus publishes the true state as PX4 `*_groundtruth` topics into the same log, so the evaluation
  needs no cross-clock alignment. Errors are displacements from the takeoff point (the EV frame has an arbitrary origin and heading).
- **Setup recorded with the data**: `machine.json` (host, CPU, GPU, driver, Docker, git commit, dirty flag, Pegasus commit),
  per-flight image ids, Isaac/PX4/ZED SDK versions, PX4 param files, world, lighting, the real-time factor during the flight, and the
  `restamp_latency_ms` the campaign flew with (read at start, since the file may change later).

### Flight profile (`tests/vio_bench.py`)

OFFBOARD only (AUTO modes refuse or fly away without GPS). Takeoff 1.2 m + 20 s hover → altitude steps 0.6 / 2.0 / 1.2 m → x and y legs
±1.5 m at 0.5 then 1.0 m/s → four 90° yaw steps → the x legs again with the body yawed 90° (body-frame velocity check) → 1.5 m square →
20 s hover → OFFBOARD descent and landing. About 133 s airborne, 25-26 m path, ~245 s wall at RTF 0.6. The profile was laid out for
Simple Room (its x+ legs cross the table edge) and fits the Warehouse's open floor unchanged.

### Configs (`tests/vio_bench.yaml`)

| config | PX4 params set live | what it isolates |
|---|---|---|
| `calibrated` | none | the shipped GPS-denied mode (`MC_YAWRATE_MAX 60`, `EKF2_EVA_NOISE 0.01`, `EKF2_OF_QMIN_GND 1`) |
| `no_yaw_limit` | `MC_YAWRATE_MAX 200` | the yaw-rate cap (peak 328 deg/s instead of 100) |
| `no_eva_fix` | `EKF2_EVA_NOISE 0.1` | the EV yaw noise fix (EKF2 heading follows the ZED, or lags it) |
| `px4_defaults` | all three above undone | the state before 2026-10-15 |
| `no_flow` | `EKF2_OF_CTRL 0` | the PMW3901 optical flow (ZED + baro + LW20 only) |
| `ev_no_position` | `EKF2_EV_CTRL 12` | ZED position fusion (ZED velocity + yaw only; position integrated) |

### Per-flight evaluation (`tests/vio_eval.py`, airborne samples)

| metric (JSON key) | definition | calibrates / indicates |
|---|---|---|
| `ekf_h_max`, `ekf_h_end`, `ekf_h_rms` | EKF2 horizontal error vs truth: max, at the end, RMS | the outcome; 0.30 m = the Phase 3 bound |
| `ekf_z_max` | EKF2 height error, max | baro + LW20 + EV velocity |
| `ev_yaw_end`, `ekf_yaw_end` | ZED / EKF2 yaw error at the end (start offset removed) | heading drift |
| `yaw_step_worst`, `yaw_rate_peak` | largest yaw error one rotation added to the ZED; peak yaw rate | `MC_YAWRATE_MAX` |
| `latency` | best lag of EV velocity vs truth (±300 ms) | `restamp_latency_ms` (residual should be ~0) |
| `vel_scale_x/y`, `vel_rmse` | LS slope and RMSE of ZED body velocity vs the camera's true velocity (incl. ω×r) | frame/sign/scale; `EKF2_EVV_NOISE` |
| `lever_fit` | camera offset fitted from the hover yaw steps minus `EKF2_EV_POS` | `EKF2_EV_POS_*` |
| `pos_noise` | std of ZED position after removing a 2 s moving average | `EKF2_EVP_NOISE` |
| `gaps`, `gap_slip`, `gap_yaw_slip` | EV gaps > 150 ms; position / yaw error change across the worst one | SDK slips |
| `pose_jump` | ZED position step > 0.10 m off truth between two samples without a gap | SDK jumps |
| `tilt_end` | ZED roll/pitch vs truth at the end | world-frame tilt (climbs leak sideways) |
| `ev_pos_fused`, `flow_fused` | fraction of samples EKF2 fused | fusion health |

Full definitions with units are in `metric_definitions` of the JSON.

**Dominant event.** Each flight is attributed to the largest of four SDK events, each normalised by its threshold: pose jump / 0.10 m,
slip at a frame gap / 0.10 m, yaw slip at a frame gap / 3°, yaw slip in a rotation / 3°. If none reaches 1, the flight is
`none (drift)` (event-free). Event-free flights show what the parameters do; flights with an event show the SDK.

### Verdict (`verify:` in `tests/vio_bench.yaml`)

| check | over | threshold |
|---|---|---|
| residual EV latency, \|median\| | every flight that flew | ≤ 20 ms (a correction is suggested above 10 ms, or above 5 ms with ≥ 3 flights) |
| ZED velocity scale x and y, median | every flight | within ±0.03 of 1 |
| lever-arm fit, \|median\| | flights with hover yaw steps | ≤ 3 cm |
| EKF2 horizontal max | every event-free `calibrated` flight (at least one) | ≤ 0.25 m |

The performance bound (0.30 m) and the event counts are reported, not gated: in the sim they are set by random SDK events. An error
above 0.25 m *without* an event means the configuration is wrong, which is what the last gate catches. The 0.25 m comes from the data of
the first ablation (event-free flights fusing ZED position ≤ 0.19 m); a first guess of 0.15 m failed a flight whose 2.0° yaw slip was
under the 3° event threshold (campaign `20261015-180905`).

### Running it

```
./bisg vio check                 # ~7 min: calibrated x 1 -> verdict
./bisg vio bench [--archive]     # ~2 h: 6 configs x 3 flights
./bisg vio bench --configs calibrated,no_flow --reps 5      # any subset; --resume <dir> continues a stopped campaign
./bisg vio report <dir>          # rebuild summary + verdict;  ./bisg vio list
python3 tests/vio_export.py <dir>... --out <file>.json      # figure-ready JSON (this page)
```
Output: `$ARCHIVE_DIR/vio_bench/<YYYYmmdd-HHMMSS>-<host>/` with `summary.md|json|csv`, `figures/*.svg`, `machine.json`,
`campaign.json|yaml|log`, and per flight `runs/<config>-r<k>/` (`flight.ulg`, `topics.npz`, `vio_eval.json`, `series.csv`,
`bench.log`, `run.json`). `--archive` copies a campaign without the `.ulg` to `archive/vio-bench/` (done for the four Simple Room
campaigns; the Warehouse ones are only in `/opt/docker-archive/vio_bench/` on Workstation A).

Primary result: the two Warehouse ablations, `20261017-121326` (restamp 95) and its replication `20261018-214421` (restamp 100), pooled
to 6 flights per config (36 flights, RTF 0.58-0.60). They differ only in the pipeline latency correction, whose residual was +5 and 0 ms.
The Simple Room ablation `20261015-152046` (RTF 0.56-0.59) is the comparison. Values are mean ± std (min-max).

**Replication.** The first run alone suggested every ablation was worse than `calibrated` (+0.010 to +0.048 m). The replication does not
confirm that for `px4_defaults` (0.111 → 0.075 m) or `ev_no_position` (0.079 → 0.070 m), which came out level with `calibrated` (0.078 m).
Pooled (exact two-sided Mann-Whitney vs `calibrated`, EKF2 h max): `px4_defaults` +0.023 m p = 0.026, `no_flow` +0.029 m p = 0.026,
`no_yaw_limit` +0.031 m p = 0.13, `no_eva_fix` +0.006 m p = 0.59, `ev_no_position` +0.004 m p = 0.82. With five comparisons none survives
a Holm correction (smallest adjusted p = 0.13). What replicates: `no_flow` and `no_yaw_limit` are ~3 cm worse in both runs;
`no_eva_fix` and `ev_no_position` are within 1 cm of `calibrated` in the Warehouse. The real separation is in the yaw metrics (§4.4) and
in the oscillation (§4.5), not in the horizontal error.

### 4.3 Simple Room vs Warehouse

| | Simple Room `20261015-152046` | Warehouse `121326` + `214421` |
|---|---|---|
| flights with an SDK event | **9 / 18** (5 yaw slips at a gap, 2 slips at a gap, 1 pose jump, 1 yaw slip in a rotation) | **1 / 36** (the oscillation flight, §4.5) |
| EV frame gaps > 150 ms, all flights | 9 | 0 |
| within 0.3 m | 13 / 18 | 36 / 36 |
| `calibrated` EKF2 h max | 0.320 ± 0.236 (0.070-0.540), 2 of 3 with an event | 0.070 ± 0.016 (0.056-0.103), none |

| ZED position noise | 7.5 mm | 4.2-4.3 mm |

The event rate differs (one-sided Fisher exact p = 7·10⁻⁵). The event-free accuracy is about the same in both worlds: the Warehouse is not
more accurate when tracking works, it loses tracking far less often. In Simple Room the events were tied to frame gaps (7 of 9); the
Warehouse had no gap in 36 flights. The cause of the gaps was not established (sim render, wrapper grab or DDS, [vio.md](vio.md)); the
Warehouse's lighting was tuned for texture (97.7 % usable pixels, `docker/sim/sim.yaml`), which plausibly helps the SDK, but these
campaigns do not isolate that.

### 4.4 Yaw rate drives the yaw slips (both worlds)

Worst yaw error added per rotation, fast-yaw flights (`no_yaw_limit`, `px4_defaults`, peak 327-417 deg/s) vs slow (the other four
configs, 99-100 deg/s):

| | fast: n, median (range) | slow: n, median (range) | two-sided Mann-Whitney p |
|---|---|---|---|
| Simple Room | 6, 5.55° (1.28-11.51) | 12, 0.98° (up to 10.04: `calibrated-r2` and 9.27: `no_eva_fix-r1`, both with an SDK event) | 0.013 (exact) |
| Warehouse, both runs | 12, 1.07° (0.30-3.23) | 24, 0.09° (up to 2.05: `214421/no_eva_fix-r3`, the oscillation flight) | < 5·10⁻⁶ (permutation, 200 000) |

In the Warehouse every fast-yaw flight slipped more per rotation than every slow flight except the oscillating one. Fast yaw also leaves
EKF2's heading further off at the end (median 0.25° vs 0.08°). `MC_YAWRATE_MAX 60` stays.

### 4.5 Yaw oscillation with `EKF2_EVA_NOISE 0.1` (found 2026-10-18)

The replication's `no_eva_fix-r3` showed 38 small "rotations" in `vio_eval`'s yaw-step list (0-20° each, peaks rising to 172 deg/s)
where the profile commands none. The ground-truth yaw rate shows a growing oscillation of the vehicle: from the velocity legs on, its RMS
roughly doubles every 10 s (4 → 8 → 17 → 37 → 68 → 107 deg/s), peaks at 228 deg/s and does not settle for the rest of the flight; EKF2's
heading swings ±3° around the truth. `121326/px4_defaults-r1` shows the same signature (RMS 3 → 6 → 12 → 26 → 55 → 171 deg/s, peak
419 deg/s), and its 4.9° ZED yaw slip, reported as an SDK event, happened inside that oscillation. During the translation legs (before
any yaw step is commanded) these two flights peak at 74 and 151 deg/s; every other flight of the three ablations, Simple Room included,
peaks at ≤ 5.5 deg/s there.

Count: 2 of the 18 flights flown with `EKF2_EVA_NOISE 0.1` (`no_eva_fix`, `px4_defaults`, three ablations), 0 of the 36 with 0.01
(one-sided Fisher p = 0.11: not significant on its own). The likely loop is EKF2's heading lagging the ZED (the v1.17 variance floor makes
0.1 an 18° yaw noise, [vio.md](vio.md) error source 2) inside the yaw controller of the sim's placeholder tune; not verified. Both flights
still stayed within 0.134 m horizontally, which is why the horizontal metrics in §4.2 do not show it. It is a further reason to keep
`EKF2_EVA_NOISE 0.01`. `vio_eval.py` has an oscillation detector since 2026-10-26 (`yaw_oscillation`: the true yaw rate swings both ways past 30 deg/s for >= 8 s on end; the ring-down after a fast yaw step is shorter). Run over all 70 campaign flights it flags exactly these two, and a flagged flight's dominant event reads `yaw oscillation (vehicle)`.

## 5. Conclusions

1. **The VIO pipeline is calibrated on Workstation A** in both worlds: residual latency 0 ms after restamp 100 (Warehouse, RTF 0.59),
   velocity scale within 0.6 %, lever arm within 1.5 cm, position noise 4 mm, reproduced in two Warehouse ablations a day apart.
   `restamp_latency_ms` moves with the machine's sim speed (85 → 95 → 100 ms over three days); rerun `./bisg vio check` on another
   machine or after a change that alters the RTF.
2. **The shipped parameters are as good as or better than every ablation** in the Warehouse (0.070 ± 0.016 m horizontal max,
   0.030 m RMS over a 26 m profile, 6/6 flights), but the horizontal-error differences are small (≤ 3 cm) and do not survive a
   multiple-comparison correction at n = 6. The parameters earn their place on yaw: the yaw-rate cap removes the per-rotation yaw slips
   (§4.4), and `EKF2_EVA_NOISE 0.01` coincides with no yaw oscillation in 36 flights (§4.5).
3. **In the sim, accuracy is set by SDK tracking events, not by parameters.** Event-free flights stay ≤ 0.19 m in every campaign; flights
   with an event reach 0.64 m. The events came with frame gaps in Simple Room and almost vanished in the Warehouse (1 of 36).
4. **ZED velocity-only fusion (`EKF2_EV_CTRL 12`)** is the robust fallback (no ZED position jump reaches EKF2: 3/3 within the bound and
   no event in Simple Room, where 9 of the other 15 flights had one). Its drift cost seen in Simple Room (0.163 vs 0.070-0.093 m
   event-free) does not show in the Warehouse (+0.004 m pooled). Kept at 13 until hardware data exists.
5. **Reliability**: 7 infra failures in 61 boots of the three ablations, all "wrapper never connected" (B18); each retry succeeded within
   3 attempts. No wrapper crash (R9) in any campaign.

## 6. Limits

- n = 3 per config per run (6 pooled in the Warehouse): the per-config means do not separate the configs after correction; pooled
  factors (yaw rate) and event counts do.
- The two Warehouse ablations differ in `restamp_latency_ms` (95 vs 100); the pooling assumes a 5 ms residual does not change the
  outcome metrics (the per-run means in §4.2 show run-to-run spread of the same order as the config differences).
- The sim ZED has no IMU (`sim.positional_tracking.imu_fusion: false`): the real ZED Mini fuses its 400 Hz IMU, so slips, tilt and
  gap effects should be smaller on hardware. The campaign calibrates the sim pipeline, not the real drone.
- A 26 m profile does not show long-flight drift: Kinetix room flights drift ~0.8 m RMS over 350 m ([todo.md](todo.md)).
- One machine. Workstation B was not campaigned; its RTF differs, so its `restamp_latency_ms` may.
- The early Warehouse checks predate the world/lighting fields (see the footnotes in §3).

Figures the data supports, and where to read them from:

| figure | data |
|---|---|
| per-config bars with every flight as a dot (any metric) | `campaigns[i].flights[].metrics.<m>` grouped by `config`, `event_free` for filled/open dots |
| ablation deltas | `per_config.<c>.delta_mean_vs_calibrated.<m>` |
| failure attribution, stacked bars | `per_config.<c>.events` |
| Simple Room vs Warehouse | the `ablation` campaigns, same keys (pool the two Warehouse ones by `config`) |
| calibration over time (restamp, residual latency, `calibrated` error) | `history[]` |
| yaw slip vs yaw rate (scatter) | `flights[].yaw_steps[]`: `peak_rate_dps` vs `ev_err_added_deg` (many steps with \|`rotated_deg`\| < 30 = the §4.5 oscillation) |
| error over time per config | the series file, mean per config over its flights |
| EKF2 error vs ZED error | series `ekf_horiz_err_m` vs `ev_horiz_err_m` |

Minimal example (matplotlib; the host has none that works with numpy 2, so use a venv: `python3 -m venv /tmp/mpl &&
/tmp/mpl/bin/pip install matplotlib`). It draws the Warehouse `ekf_h_max` bars: mean ± std per config, every flight as a dot, open
dot = flight with an SDK event:
```python
import json, matplotlib.pyplot as plt
d = json.load(open("docs/data/vio_campaigns.json"))
c = next(c for c in d["campaigns"] if c["id"] == "20261017-121326-stallman2")
cfgs = c["configs_flown"]
for i, cfg in enumerate(cfgs):
    fl = [f for f in c["flights"] if f["config"] == cfg and f["metrics"]]
    s = c["per_config"][cfg]["stats"]["ekf_h_max"]
    plt.bar(i, s["mean"], yerr=s["std"], alpha=0.35, capsize=4)
    for k, f in enumerate(fl):
        plt.plot(i - 0.15 + 0.15 * k, f["metrics"]["ekf_h_max"], "o", mfc="C%d" % i if f["event_free"] else "white", mec="C%d" % i)
plt.axhline(0.30, ls="--", c="r", label="0.30 m bound")
plt.xticks(range(len(cfgs)), cfgs, rotation=30); plt.ylabel("EKF2 horizontal error, max [m]"); plt.legend(); plt.tight_layout()
plt.savefig("ekf_h_max.png", dpi=200)
```
