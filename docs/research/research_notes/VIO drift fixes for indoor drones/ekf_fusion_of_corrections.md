## Q1. PX4 EKF2 external vision (v1.14 to v1.17): reset_counter, quality, gates, EV_CTRL, noise mode, the EV position bias estimator, and long-rejection resets

### Takeaway
In EKF2 a change in `reset_counter` is not a "smooth this jump" signal. It is a "teleport" command. With no GNSS active, EKF2 immediately snaps its horizontal position (and height, when EV is the height reference) to the new EV value, re-seeds the EV-to-EKF yaw-alignment filter, resets yaw to EV yaw if EV yaw fusion is active, and resets velocity only if EV velocity is the sole horizontal aiding source. The EV position "bias estimator", the only mechanism that absorbs an offset gradually, runs only while GNSS position fusion is active, so it never helps indoors. Without a reset_counter bump, a big jump is rejected by a per-axis 5-sigma gate (`EKF2_EVP_GATE`). After 1 s (hard-coded, not a parameter) of continuous rejection, with quality OK, EKF2 hard-resets to EV anyway, up to 5 times per flight (counted only in air), and then stops EV position fusion.

### Inferences
- Indoors with no GNSS, EV is the position reference, so there is no gradual-absorption path in EKF2. A loop-closure jump fed directly to EKF2 has three possible outcomes. (a) A jump smaller than ~5·sqrt(var_ev + var_state) per axis is fused as an ordinary measurement. The Kalman gain pulls position over a few updates and puts the residual into velocity and accel-bias states, which gives a velocity transient the position controller reacts to. (b) A larger jump is rejected for 1 s, then hard-reset (a teleport, and the controllers shift setpoints only in onboard modes). (c) After 5 in-air resets, EV position fusion stops and the vehicle loses position aiding.
- Bumping `reset_counter` turns case (b) into an immediate, clean reset with no 1 s of rejected data. It also re-seeds the yaw-alignment filter, which matters when the loop closure includes a yaw correction and the frame is FRD. It does not make the jump smaller.
- Because `_ev_sample_prev` updates only on good-quality samples, sending a reset with `quality` below `EKF2_EV_QMIN` stops EV pos/vel/yaw/hgt fusion until quality recovers. That makes a forced re-start, which resets position again.
- If the offboard companion holds position setpoints in the PX4 local frame, every EKF position reset displaces the vehicle unless the companion applies `delta_xy` itself (per #19830).

## Q2. MAVLink ODOMETRY (#331) fields, and how MAVROS (ROS 2) maps nav_msgs/Odometry (does it pass reset_counter?)

### Takeaway
MAVLink defines `reset_counter` exactly for this case ("when e.g an external SLAM system detects a loop-closure and the estimate jumps"). The MAVROS ROS 2 `odometry` plugin never sets it: it stays 0, `quality` stays 0, `estimator_type` is VISION and `frame_id` is LOCAL_FRD. The `vision_pose` plugin also leaves `reset_counter` unset. A MAVROS-fed EKF2 therefore never sees an EV reset. The ways to send one are to patch the plugin, send a hand-built ODOMETRY, or bypass MAVROS with uXRCE-DDS `/fmu/in/vehicle_visual_odometry` (px4_msgs/VehicleOdometry has `reset_counter` and `quality`).

This is designed to be used when e.g an external SLAM system detects a loop-closure and the estimate jumps." `estimator_type` (MAV_ESTIMATOR_TYPE). `quality` (int8, %): "-1 = odometry has failed, 0 = unknown/unset quality, 1 = worst quality, 100 = best quality". `pose_covariance`/`velocity_covariance`: 21-element upper-right triangle, "If unknown, assign NaN value to first element" — [MAVLink common.xml](https://github.com/mavlink/mavlink/blob/master/message_definitions/v1.0/common.xml); [mavlink.io ODOMETRY](https://mavlink.io/en/messages/common.html#ODOMETRY)

## Q3. REP 105 map → odom → base_link: how loop-closing SLAM keeps odom continuous, which frame to send to the flight controller, and PX4 guidance

### Takeaway
REP 105 requires `odom` to be continuous ("without discrete jumps") and puts all loop-closure and relocalization jumps into `map → odom`. robot_localization, Isaac ROS VSLAM and the ZED wrapper all publish `map → odom` for this reason. The PX4 VIO docs say that when position and loop closing disagree with another source, "it is more reliable to just use vision velocity". **ZED-specific trap:** the ZED ROS 2 wrapper's default `reset_odom_with_loop_closure: true` makes the `odom` topic itself jump. On a loop closure it sets odom→base to identity (pose back to the origin) and publishes a zero twist for that frame. That breaks REP 105 continuity for anything feeding `odom` to PX4.

### Cited Findings
- REP 105: odom "can drift over time, without any bounds … However, the pose of a robot in the odom frame is guaranteed to be continuous, meaning that the pose of a mobile platform in the odom frame always evolves in a smooth way, without discrete jumps." map "is not continuous, meaning the pose of a mobile platform in the map frame can change in discrete jumps at any time … discrete jumps in position estimators make it a poor reference frame for local sensing and [acting]". A localization component "does not broadcast the transform from map to base_link. Instead, it first receives the transform from odom to base_link, and uses this information to broadcast the transform from map to odom." — [REP 105 source](https://github.com/ros-infrastructure/rep/blob/master/rep-0105.rst); [REP 105](https://www.ros.org/reps/rep-0105.html)
- robot_localization: "If you are only fusing continuous position data such as wheel encoder odometry, visual odometry, or IMU data, set world_frame to your odom_frame"; if "fusing global absolute position data that is subject to discrete jumps (e.g., GPS or position updates from landmark observations)", set `world_frame` to `map_frame`, and the filter then computes and broadcasts map→odom rather than map→base_link. The GPS tutorial recommends two instances: one fusing only continuous data in `odom` ("Execute local path plans and motions in this frame") and one fusing everything in `map` — [robot_localization state_estimation_nodes.rst](https://github.com/cra-ros-pkg/robot_localization/blob/ros2/doc/state_estimation_nodes.rst); [integrating_gps.rst](https://github.com/cra-ros-pkg/robot_localization/blob/ros2/doc/integrating_gps.rst)
- robot_localization outlier gating: `odomN_pose_rejection_threshold`, `poseN_rejection_threshold`, etc. are "expressed as Mahalanobis distances … Each defaults to numeric_limits<double>::max()" (i.e. off by default) — [state_estimation_nodes.rst](https://github.com/cra-ros-pkg/robot_localization/blob/ros2/doc/state_estimation_nodes.rst)
- ZED ROS 2 wrapper config (`common_stereo.yaml`, master): `publish_tf: true # publish odom -> camera_link`, `publish_map_tf: true # publish map -> odom`, `area_memory: true # Enable to detect loop closure`, `reset_odom_with_loop_closure: true # Re-initialize odometry to the last valid pose when loop closure happens (reset camera odometry drift)`, `set_gravity_as_origin: true`, `two_d_mode: false` — [zed-ros2-wrapper common_stereo.yaml](https://github.com/stereolabs/zed-ros2-wrapper/blob/master/zed_wrapper/config/common_stereo.yaml#L117-L141)

- ZED docs: `odom` = "Odometry pose referred to odometry frame"; `pose` = "Camera pose referred to Map frame (complete data fusion algorithm is applied)", with area-memory loop closure and relocalization — [Stereolabs ZED node docs](https://www.stereolabs.com/docs/ros/zed-node/); [Stereolabs ROS 2 positional tracking](https://www.stereolabs.com/docs/integrations/ros-2/positional-tracking); community: `area_memory: false` "Disables loop closure computation" while the pose topic becomes pure VIO — [Stereolabs forum: Area Memory ROS2](https://community.stereolabs.com/t/area-memory-ros2/9213)
- Isaac ROS Visual SLAM publishes map → odom → base when `publish_map_to_odom_tf` and `publish_odom_to_base_tf` are both true (NVIDIA forum report; not official documentation) — [NVIDIA forum](https://forums.developer.nvidia.com/t/isaac-ros-visual-slam/351148)
- PX4 VIO troubleshooting, on using vision position for loop closing alongside GPS: "This is really difficult, because when they disagree it will confuse the EKF … From testing it is more reliable to just use vision velocity." It also requires `/mavros/odometry/out` plus a `CompanionProcessStatus` with component 197 — [PX4 VIO docs](https://docs.px4.io/main/en/computer_vision/visual_inertial_odometry)
- PX4 external-position docs: "When using the MAVROS odom plugin, it is important that no other node is publishing a transform"; "Yaw angle should be zero when body and reference frame align"; tune `EKF2_EV_DELAY` "to find the value that yields the lowest EKF innovations during dynamic maneuvers" — [PX4 external position estimation](https://docs.px4.io/main/en/ros/external_position_estimation)
- Published practice: VINS-Mono's quadrotor feedback-control experiment ran with "Loop closure is disabled for this experiment", using 100 Hz VIO estimates. Loop closure and relocalization run in a separate 4-DOF (x, y, z, yaw) pose graph "to eliminate drift" — [Qin, Li, Shen, VINS-Mono, IEEE T-RO 2018, arXiv:1708.03852](https://arxiv.org/abs/1708.03852)
- GOMSF (Mascaro, Teixeira, Hinzmann, Siegwart, Chli; ICRA 2018) is a decoupled fusion of 6-DoF VIO with global positions, framed as a real-time alignment between the VIO base frame and the global frame. That is the map→odom idea for MAVs — [ETH Research Collection](https://www.research-collection.ethz.ch/bitstream/20.500.11850/305564/1/ICRA18_0836_FI.pdf) (abstract via search; full text not read). VINS-Fusion's global fusion (Qin et al. 2019, arXiv:1901.03642) likewise aligns local VIO into a global frame through a pose graph — [arXiv:1901.03642](https://arxiv.org/abs/1901.03642)

### Inferences
- For a PX4 + MAVROS + ZED stack, the safe default is to send ZED `odom` (continuous) to PX4 with `reset_odom_with_loop_closure: false`, or `area_memory: false` on the PX4-facing instance. Keep loop-closure and map corrections in map→odom on the companion and apply them in the planner or setpoint layer (transform goals from map to odom before sending to PX4). Drift then shows up as a slowly growing offset between map goals and the PX4 frame, never as an EKF jump.
- If you instead send the ZED `pose` (map frame), every loop closure is a pose step in EKF2 (see Q1 outcomes), and the step must be flagged with `reset_counter`, which stock MAVROS cannot do.
- With the stock ZED default (`reset_odom_with_loop_closure: true`), feeding `odom` to PX4 is the worst case. The pose jumps to (0,0,0) with identity heading in the odom frame and the twist for that frame is zero. With no `reset_counter`, that is a large rejected innovation, a 1 s hard reset to the origin, and a burned reset count.

## Q4. Robust handling of VIO jumps and outliers in filters (gating, robust KFs, multi-hypothesis, FDE, published drone systems)

### Takeaway
Production autopilots (PX4 EKF2) use per-axis normalized-innovation gates plus timeout-driven resets and a fixed reset budget. They do not use robust M-estimators or multi-hypothesis tracking for EV. Robust options in the literature include chi-square/Mahalanobis gating, Student-t and Huber robust Kalman filters, and switchable or max-mixture constraints in pose graphs. Their common caveat: a gate alone cannot tell a "legitimate correction" (loop closure) from an outlier, which is why systems separate the correction into a frame transform (map→odom), or flag it explicitly (reset_counter), rather than fusing it as a measurement.

### Cited Findings
- PX4 EKF2's innovation test: per component, `test_ratio = innov² / (gate² · innov_var)`, rejected if > 1 (ekf.h, release/1.17). The PX4 EKF guide: "All observations have a statistical confidence checks applied to the innovations … controlled by the EKF2_*_GATE parameter", and rejection "for long enough" makes "the EKF … attempt a reset of the states using the sensor observations" — [ekf.h](https://github.com/PX4/PX4-Autopilot/blob/release/1.17/src/modules/ekf2/EKF/ekf.h); [PX4 EKF guide](https://docs.px4.io/main/en/advanced_config/tuning_the_ecl_ekf#observation-errors)
- PX4 EKF numerical guards: if a covariance update would produce negative variance, "The state and covariance update is skipped", the rows and columns are reset and `filter_fault_flags` is set; variances are bounded and symmetry is forced — [PX4 EKF guide](https://docs.px4.io/main/en/advanced_config/tuning_the_ecl_ekf#ekf-numerical-errors)
- robot_localization exposes Mahalanobis-distance rejection thresholds per sensor, off by default — [robot_localization docs](https://github.com/cra-ros-pkg/robot_localization/blob/ros2/doc/state_estimation_nodes.rst)
- "Robust Outlier-Adaptive Filtering for Vision-Aided Inertial Navigation" (Sensors 2020, UAV VINS): front-end outlier removal plus a back-end statistical test comparing Mahalanobis distances against chi-square quantiles (typically 95%) — [MDPI Sensors 20(7):2036](https://www.mdpi.com/1424-8220/20/7/2036)
- A Gaussian-Generalized-Inverse-Gaussian joint MSCKF (IEEE TAES 2022) notes the chi-square test is the usual MSCKF outlier remover and that choosing its threshold is difficult, motivating heavy-tailed noise models — [White Rose eprint](https://eprints.whiterose.ac.uk/id/eprint/191632/1/A%20Gaussian-Generalized-Inverse-Gaussian%20Joint%20MSCKF%20-%20TAES%20Oct%202022.pdf)
- A chi-square-test-based robust Kalman filter (INS/SRS/CNS, Sensors 2020) uses the test to detect faults and adapt the measurement noise — [PMC7588989](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC7588989/)
- Agamennoni, Nieto, Nebot, "An outlier-robust Kalman filter", ICRA 2011 (Student-t, variational) — citation only, via [Robust Gaussian Filtering using a Pseudo Measurement, arXiv:1509.04072](https://arxiv.org/pdf/1509.04072)
- Sünderhauf & Protzel, "Switchable constraints for robust pose graph SLAM", IROS 2012, pp. 1879-1884: the optimizer can "recognize and reject outliers … by making the topology of the underlying factor graph … subject to the optimization". Limitations noted later: an extra variable per loop closure, and failure above some outlier ratio — [QUT eprints](https://eprints.qut.edu.au/109582); [AEROS, Frontiers 2022](https://www.frontiersin.org/journals/robotics-and-ai/articles/10.3389/frobt.2022.789444/pdf)
- Pose-graph robust back-ends: convex relaxations with outliers (arXiv:1801.02112), efficient graduated non-convexity (arXiv:2310.06765), riSAM (arXiv:2209.14359) — [arXiv:1801.02112](https://arxiv.org/pdf/1801.02112); [arXiv:2310.06765](https://arxiv.org/pdf/2310.06765); [arXiv:2209.14359](https://arxiv.org/pdf/2209.14359)
- SIMSF (IEEE Access 2020) extends GOMSF-style VIO-to-global alignment to a similarity transform and adds VO/VIO fault detection — [DOAJ record](https://doaj.org/article/9aeaf3fa22714ef4b183795cde34de25)
- 2026 example: FusionCore, a 23-state UKF for ROS 2 with per-sensor chi-square gates including a 6-DoF visual-SLAM pose gate — [arXiv:2605.25239](https://arxiv.org/pdf/2605.25239)
- An indoor UAV ESKF with multi-epoch, VIO-constrained outlier rejection of UWB (2025) — [PMC12737027](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC12737027/)

### Inferences
- EKF2's gate is per-axis, and 5 SD is wide (indoor EV variance floor 0.1 m → gate ≥ 0.5 m with zero state variance). Sub-gate loop-closure steps of tens of centimetres will be fused, not rejected, and become velocity transients. Tightening `EKF2_EVP_GATE` converts more of them into the 1 s-reject-then-reset path. Neither is "smooth".
- For a companion-side guard, a practical pattern from these sources: Mahalanobis-gate each VIO delta against the IMU or EKF prediction (robot_localization-style threshold). On an accepted discrete correction, re-anchor via map→odom (or increment `reset_counter` if position must be fed in map). Use `quality` (with `EKF2_EV_QMIN` > 0) to drop EV fusion during ZED tracking-state degradation instead of letting bad samples through.

- I did not read the full text of Huber-based KF papers (e.g. Gandhi & Mili, IEEE TSP 2010; Karlgaard & Schaub 2007), so they are not cited.

## Q5. Velocity-only vs position EV fusion, gradual blending vs step resets, and heading resets without a magnetometer

### Takeaway
Velocity-only EV fusion (`EKF2_EV_CTRL` bit 2, optionally with yaw bit 3) is immune to loop-closure position jumps, because a continuous VIO's velocity does not jump, and PX4's VIO docs recommend it when position sources disagree. The cost is unbounded horizontal position drift in EKF2. EKF2 has no built-in "blend the correction over N seconds" mode. Indoors, a position correction is either fused through the normal gain (sub-gate) or applied as a step reset. Gradual blending has to be done upstream: rate-limit the map→odom correction you inject, or apply it at the setpoint layer. Without a magnetometer, EV yaw (bit 3) is the heading reference. Any EV yaw jump becomes an EKF yaw reset (on `reset_counter`, or after 1 s of rejection), and in 1.17 the yaw noise floor is mis-scaled.

### Cited Findings
- PX4 VIO docs: "From testing it is more reliable to just use vision velocity" when loop-closing vision position conflicts with another source — [PX4 VIO](https://docs.px4.io/main/en/computer_vision/visual_inertial_odometry)
- EKF2 EV velocity is gated at `EKF2_EVV_GATE` (default 3 SD), rejects |v| > `EKF2_VEL_LIM`, and resets velocity on `ev_reset` only if EV velocity is the sole horizontal aiding source — [ev_vel_control.cpp](https://github.com/PX4/PX4-Autopilot/blob/release/1.17/src/modules/ekf2/EKF/aid_sources/external_vision/ev_vel_control.cpp#L54-L116); [params](https://github.com/PX4/PX4-Autopilot/blob/release/1.17/src/modules/ekf2/params_external_vision.yaml)
- Only one gradual-offset mechanism exists in EKF2 EV: the position bias estimator, active only with `gnss_pos`, and the height bias estimator, active with EV height when EV is not the height reference — [ev_pos_control.cpp](https://github.com/PX4/PX4-Autopilot/blob/release/1.17/src/modules/ekf2/EKF/aid_sources/external_vision/ev_pos_control.cpp#L73-L78); [ev_height_control.cpp](https://github.com/PX4/PX4-Autopilot/blob/release/1.17/src/modules/ekf2/EKF/aid_sources/external_vision/ev_height_control.cpp#L111-L127)
- Mode requirements: a position mode "requires IMU data, a source of yaw (magnetometer or external vision) and a source of height data". With mag type None, "The estimator will use other sources of heading: GPS heading or external vision" — [PX4 EKF guide](https://docs.px4.io/main/en/advanced_config/tuning_the_ecl_ekf)
- EV yaw on an FRD frame resets yaw to EV at start and sets `yaw_align=false` (heading relative to EV frame). It resets yaw on each `ev_reset` and after 1 s of rejection (5 in-air resets), gated by `EKF2_HDG_GATE` 2.6 SD — [ev_yaw_control.cpp](https://github.com/PX4/PX4-Autopilot/blob/release/1.17/src/modules/ekf2/EKF/aid_sources/external_vision/ev_yaw_control.cpp#L86-L183); [module.yaml](https://github.com/PX4/PX4-Autopilot/blob/release/1.17/src/modules/ekf2/module.yaml)
- v1.17 EV yaw variance floor uses `EKF2_EVA_NOISE` unsquared (fixed in `main`). The local bench notes the same quirk ("effective std = sqrt(EVA_NOISE)", vio_eval.py L16) — [1.17 ev_yaw_control.cpp L48](https://github.com/PX4/PX4-Autopilot/blob/release/1.17/src/modules/ekf2/EKF/aid_sources/external_vision/ev_yaw_control.cpp#L48); /home/bisg/Documents/github/bisg_isaac/tests/vio_eval.py
- Heading resets are published as `delta_heading`/`heading_reset_counter` in vehicle_local_position — [VehicleLocalPosition.msg](https://github.com/PX4/PX4-Autopilot/blob/release/1.17/msg/versioned/VehicleLocalPosition.msg)
- The local bench already has a velocity+yaw-only ablation, `EKF2_EV_CTRL: 12` ("ZED velocity + yaw only, no ZED position; position from velocity + flow") — /home/bisg/Documents/github/bisg_isaac/tests/vio_bench.yaml L38-L39

### Inferences
- Trade-off summary for indoor PX4 + ZED:
  - (A) EV_CTRL = vel + yaw (12), optionally + hgt: no position jumps ever reach EKF2. Position drifts at the VIO velocity-error rate (plus flow if used). Loop-closure corrections must be applied by the companion in map→odom at the planner level. The yaw-jump risk remains, unless yaw is also continuous (ZED odom with `reset_odom_with_loop_closure: false`).
  - (B) EV_CTRL includes position, fed from continuous `odom`: bounded short-term drift, no jumps. Same need for companion-side map→odom.
  - (C) EV position fed from `map`/`pose`: drift-free EKF position, but every correction is an EKF step, and you need `reset_counter` (not available through stock MAVROS) and offboard setpoint compensation via `delta_xy`.
- "Blend" option for (C): instead of a step, ramp the injected map→odom correction at a bounded rate (e.g. a few cm/s and deg/s) so each EV sample's innovation stays well under the 5 SD position gate and 2.6 SD heading gate. EKF2 then absorbs it as ordinary measurements. This is an engineering inference, not a documented PX4 practice. The rate must stay below what the position controller tracks smoothly, and the EV covariance must not be shrunk below the real step size.
- Yaw resets without a magnetometer are the most dangerous case. A yaw step rotates the EKF heading. In FRD EV mode without EV yaw, the position mapping `R_ev_to_ekf` changes, so a yaw correction far from the EV origin becomes a large position innovation. Keep EV yaw continuous (odom frame) and apply heading corrections only in map→odom.

- I did not confirm whether `resetQuatStateYaw` rotates velocity or position states, which affects how violent a yaw reset is (see Q1 Gaps).
