# bisg_isaac — project instructions for Claude Code

Isaac Sim 6.0 + Pegasus + PX4 digital twin of a Jetson Orin NX / Pixracer / ZED Mini drone (swarm later), ROS 2 Jazzy in containers + MAVROS, Docker-first.
Read `docs/plan.md` for architecture, `docs/todo.md` for what is in progress. Update `docs/todo.md` when you finish work.

## Ground rules
- This is a **fresh start**. Do not pull code from `~/isaacsim` or `~/swarm_ws` (earlier, abandoned attempts). Ideas may be re-implemented; files are not copied.
- Build **gradually, phase by phase** (`docs/roadmap.md`). Do not start a later phase unless asked; do not widen scope.
- Sim and hardware obey `docs/interface-contract.md`. A new topic, frame or namespace is added there first.
- PX4 <-> ROS 2 bridge is **MAVROS** (ADR-001), not uXRCE-DDS — decided after the PX4-link study (`archive/px4-link-study/`): lean plugin list `docker/ros/mavros_lean.yaml`, applied by `docker/px4-bridge/entrypoint.sh` (`MAVROS_PLUGINS=full` for the stock list). The PX4 bridge is **one compose service, `px4-bridge`** (image `bisg/px4-bridge`, entrypoint `docker/px4-bridge/entrypoint.sh`, env only), and `PX4_BRIDGE=mavros|mavsdk|xrce|none` (or a list, `mavros,xrce`) in `config/bisg.conf` says which bridge(s) it runs, one container per drone and bridge (`bisg-<bridge>-N`); `./bisg px4-bridge plan|up|status|params` operates it (`docs/px4-bridge.md`). MAVROS stays the default and the only one the ZED bridge and the tests use.
- Every runtime component has a Dockerfile / compose service (ADR-002). **One `docker/compose.yaml` serves the x86_64 workstation and the arm64 Jetson** (no `deploy/` folder): profiles `sim`/`sim-headless`/`zed` are workstation-only, `drone` is the real drone (`./bisg drone up`, MAVROS on `/dev/px4` + the ZED stack on the real camera), `ros`/`tools` run on both; the only per-arch difference is the ZED image tag (`ZED_VARIANT`: `desktop` on x86_64, `jetson` on aarch64, set by `scripts/_common.sh`; `docker/zed/build.sh jetson` reads the board's L4T, e.g. R39.2.1, from `/etc/nv_tegra_release`). Each image's config lives in its folder (`docker/sim/configs`, `docker/ros/mavros_lean.yaml`, `docker/zed/zed.yaml`). Host installs are for debugging only.
- Version pins live in `docs/plan.md` §4 and are applied from the pins block of `config/bisg.conf`. Change a pin only with an ADR update.
- Settings layering (`docs/configuration.md`): `config/bisg.conf` = every project default, in topic comment blocks (view, sim, ros, drone, pins, links); `docker/zed/zed.yaml` = everything the ZED does (SDK modules, PX4 bridge, QGC video; ADR-008); `docker/.env` = this machine only; scenario YAML = world/vehicle content. A new knob goes in the matching block + `conf_default` in `scripts/_common.sh`, never hard-coded in a script. One key lives in exactly one place.
- One key, `SIM_VIEW`, decides window + remote view: `gui|headless|web|webrtc|both|auto`, combined with `+` (`gui+webrtc`); `./bisg up <value>` overrides it per run. `web` (still frames on one TCP port) survives a VS Code/SSH tunnel; `webrtc` needs UDP 47998, so LAN or Tailscale only (`docs/remote-access.md`).
- **Remote access from another network** is the `tailscale` compose service (Tailscale, ADR-009; `./bisg tailscale up|login|status|down`; login only in a browser via `./bisg tailscale login` — never auth keys), own compose project; `TAILSCALE_WITH_SIM=1` (default, ADR-009 amended 2026-10-20) makes it follow the sim: `./bisg up|all` connect, `./bisg down|stop` disconnect, `restart` keeps it (host daemon: `tailscale up|down`, needs `sudo tailscale set --operator=$USER` once). `SIM_VIEW_ADDR=tailscale` (in `docker/.env`) advertises the tailnet IP. Tunnels (SSH/Cloudflare) carry only the `web` view, never WebRTC's UDP. No ZeroTier.
- Containers are ROS 2 **Jazzy** (ADR-005), Ubuntu 24.04 base. A host ROS 2 Jazzy is optional, for debugging only (`sudo scripts/install_host_ros.sh`, then `source scripts/host_ros_env.sh`); never make a script depend on host ROS.
- Order: single-drone twin → assets/models → one real drone → swarm. Swarm work waits for Phase 6.
- Never `git submodule update --remote` in `docker/sim/PegasusSimulator` or `docker/zed/zed-ros2-wrapper` without checking the pin.
- **Isaac Sim 6.0 stack** (migrated from 5.1 on 2026-10-02; `archive/docs/migration-report.md`, errors/gotchas in `docs/migration-errors.md`, rollback = git tag `isaac-5.1-baseline`, local only — never pushed). Isaac 6.0 + Python 3.12 + Pegasus **PR #144 head + local commits** from our fork `akashshingha850/PegasusSimulator`, branch `local` (no release tag exists; ADR-010: push a new local commit to the fork before pinning it) + PX4 v1.17.0. The 5.1 APIs are gone: no `omni.isaac.core`, `World`, `dynamic_control`, `isaacsim.core.api`/`core.utils` (deprecated). Use `SimulationManager` / `RenderingManager`, `isaacsim.core.experimental.*`, `isaacsim.sensors.experimental.physics`; the launcher loop is `simulation_app.update()`. Bundled ROS libs are `exts/isaacsim.ros2.core/jazzy`. The 6.0 shader cache lives in `/isaac-sim/kit/cache` (volume `isaac-cache-kit`) — without it every boot recompiles shaders (190 s instead of 30 s).
- **The ZED stack** (`docs/zed-stack.md`, ADR-008, skill `zed-sdk`): **`docker/zed/zed.yaml` is the only place that configures the ZED** — a block per SDK module in the wrapper's own key names (validated against the wrapper's YAML), `services:` (`px4_bridge`: health / odometry / obstacle_distance; `qgc_video`) and a `sim:` block for the sim-only deltas. `./bisg zed plan|set|up|services|enable|status|logs|check|test|down`. Code in `zed_stack/` (compiler, bridge, video), one image `bisg/zed` for wrapper + bridge + video, same compose file for sim and drone. Never hard-code wrapper params anywhere else; a new bridge module needs a case in `tests/zed_bridge_fake.py`.
- **The real ZED SDK runs in the sim** (the only ZED source; `docs/zed-sdk-sim.md`): Stereolabs' `zed-isaac-sim` v5.2.x extension streams a ZED Mini twin into the unmodified `zed_wrapper` (`./bisg zed build|image|up|check`). The emulated rig and `vio_mock` were removed 2026-10-07 (ZED is SDK-only). **The sim default is GPS-denied** since 2026-10-15, like the real drone: `docker/sim/sim.yaml` `px4_params: [raptor, ekf2_vio_flow_range]` (baro height reference + LW20 + ZED VIO + PMW3901, no GPS/mag; `docs/range-flow.md`) and the bridge's ZED odometry is on in the sim too. Without GPS, PX4's AUTO.TAKEOFF/LOITER/LAND refuse or fly away: tests take off and land in OFFBOARD (`tests/mav_offboard.py` raw MAVLink, `vio_flight.py` over MAVROS). The ZED asset must be **fixed-jointed** to the vehicle body (a nested reference does not follow it: black frames, odom 0). The wrapper is launched by `docker/zed/zed_drone.launch.py` in sim and on the Jetson. ZED topic names are the 5.4.1 ones (`left/color/rect/image`, not `image_rect_color`). The SDK connects once per sim run (B18): never `zed up` twice against one sim run. R9 (`can't compare times with different time sources`) is fixed since 2026-10-21 by pinning the wrapper to upstream master `b19902d` (`ZED_WRAPPER_REF`, ADR-011; no release has the fix yet); the `zed` service still preloads `docker/zed/debug/terminate_bt.cpp`, so `docker logs bisg-zed-1 | grep terminate_bt` shows the throw site of any other uncaught exception. The ZED_M asset authors its `Imu_Sensor` 90 deg rotated; `zed_sdk_rig.py` sets it body-aligned (`STREAM_IMU_RPY`, 2026-10-22), after which the wrapper's IMU matches the physics IMU. Since 2026-10-23 the sim tracks exactly like the real camera (AUTO = GEN_3 + IMU fusion, no `sim:` tracking delta): `zed_sdk_rig.py StreamImuFeeder` feeds the physics IMU every physics step into the stream via the extension patch `docker/zed/patches-isaac-ext/0001` (`ingest_imu`, gen-2 streaming, gyro in deg/s; `restamp_latency_ms` 95). Local fixes are patch files applied around the build and reverted after: wrapper `docker/zed/patches/*.patch` (`docker/zed/build.sh`), extension `docker/zed/patches-isaac-ext/*.patch` (`build_isaac_ext.sh`; the clone is git-ignored, the patch is the only record). Isaac 5.1 has no ZED Mini twin.
- **The default world is the Warehouse** (since 2026-10-17, for Kinetix whole-room photogrammetry): `docker/sim/sim.yaml` `world: Warehouse`, spawn (-2.5, 0, 0.11), no scan objects, `light_scale: 0.5` + `ambient_light: 2.0` (exposure for photogrammetry; `launch.py` applies them); emptied since 2026-10-22 by `keep_only` (floor + stripes, walls, ceiling + roof beams, lights; racks/pallets/signs/lamps deactivated) and `drop` (the hanging roof trusses, a sub-mesh of the wall-column asset); lighting re-probed there, unchanged. Older measurements in vio.md / range-flow.md / performance.md / zed-benchmark.md were taken in Simple Room and say so.
- Before trusting a sim run after any pin/API change, run the three checks that gate the migration: `./bisg smoke`, `tests/vio_flight.py --alt 1.2 --side -1.0` (on the default `./bisg all headless`; `single_iris_vio` has no ToF/flow and fails on the sim ZED's z drift), `tests/zed_depth_box.py` (`single_iris_vio`); after a ZED-stack change also `./bisg zed test` (no sim needed); after an EKF2 / ZED-calibration change (`ekf2_vio_flow_range.params`, zed.yaml odometry/restamp) also `./bisg vio check` (~7 min, verdict = VIO pipeline calibrated on this machine; full ablation `./bisg vio bench`, docs/vio.md). Sim speed on 6.0 is ~0.5-0.6x real time with the ZED twin (the camera renders cost it, not Pegasus: `docs/performance.md`); time-based test margins must allow for it.

## Host facts (two workstations)
The project must run unchanged on both; anything machine-specific goes in `docker/.env` (git-ignored), never in `config/bisg.conf` or a script. Check which box you are on with `hostname` / `nvidia-smi` before trusting a path or GPU figure below.

**Workstation A — user `bisg`, 1x RTX 4500 Ada**
- Ubuntu 24.04.5 LTS, host ROS 2 optional (debug only; `scripts/install_host_ros.sh`), RTX 4500 Ada Generation 24 GB VRAM, NVIDIA driver **580.178.04**, Docker 29.1.3, 125 GB RAM, 24 cores.
- **Docker's data-root is `/opt/docker-data`** (moved from `/var/lib/docker` on 2026-10-03 because `/` is only 140 GB; `/etc/docker/daemon.json`, backup `daemon.json.bak-before-datarootmove`). `./bisg check` prints the root and its free space.
- Bulk storage lives on `/opt` (1.9 TB ext4, ~1.3 TB free) — **not** `/media/ubuntu/ssd`, which does not exist on this box. `ARCHIVE_DIR` and any large-artifact paths must point under `/opt` (set in `docker/.env`).
- Isaac Sim 6.0 verified: ~30 s to `sim ready` warm, ~190 s on the first boot or after `./bisg debug clean-cache`.

**Workstation B — `ict-em018kc6`, user `akashshingha`, 2x RTX 6000 Ada, shared**
- Ubuntu 24.04.3 LTS, no ROS install on host, 2x RTX 6000 Ada Generation 48 GB VRAM, NVIDIA driver **580.105.08**, Docker 29.1.3 (data-root default `/var/lib/docker`, `/` is a 3.7 TB LV), 188 GB RAM, Threadripper PRO 7975WX (64 threads). Multi-user machine: do not touch other users' processes.
- **GPU contention:** the user's vLLM server (`systemctl --user` unit `lc-chat.service`, ~46 GB on each GPU) leaves too little VRAM for Isaac (PhysX "fail to launch kernel", then crash ~45 s into boot). It is disabled since 2026-10-06; `systemctl --user start lc-chat` brings it back — stop it again before a sim run. Check `nvidia-smi` first when the sim crashes on boot here.
- Isaac Sim 6.0 + `./bisg smoke` + MAVROS verified 2026-10-06: ~55 s to `sim ready` + PX4 ready (headless).

**Both**
- Driver must stay on the 580 branch — the 595.x/R590 branch segfaulted Isaac Sim 5.1's RTX renderer (`docs/plan.md` §12; untested on 6.0); `scripts/check_env.sh` hard-fails on any 59x driver. Keep that guard.
- GPU access from containers needs the user in the `docker` group + NVIDIA Container Toolkit (`./bisg check`, `docker run --gpus all`). After adding a user to the group, a fresh login (or `newgrp docker` / `sg docker -c ...`) is needed before the socket works.
- Use `timeout` and `PYTHONUNBUFFERED=1` when driving the sim from scripts; prefer headless for tests.
- Debug recording: `./bisg bag` (rosbag2/MCAP, `docker/ros/bag.yaml` holds the topic profiles and `enabled:` autostart switch, bags in `BAG_DIR`). Never put raw image/depth topics in a default profile (3.7 MB a frame).
