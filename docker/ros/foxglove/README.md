# Foxglove web UI and layouts

`./bisg ros start foxglove` (on by default, docker/ros/tools.yaml) starts the bridge (`ws://<host>:8765`, in bisg-ros) and its web UI,
the `lichtblick` compose service (Lichtblick, the open-source Foxglove Studio fork; pinned `LICHTBLICK_TAG`, port `FOXGLOVE_UI_PORT`=8080
in config/bisg.conf). It prints the URL; open it in VS Code with "Simple Browser: Show":

    http://localhost:8080/?ds=foxglove-websocket&ds.url=ws://localhost:8765&layoutUrl=http://localhost:8080/layouts/raptor.json

`ds` connects to the bridge; `layoutUrl` loads `raptor.json` from this folder (served at `/layouts/`) on every page load and replaces
the stored "raptor" layout, so the repo file always wins. Changes you make in the UI are lost on the next load unless you save them
under another name (Layouts menu) or put them into `make_layout.py`. Without `layoutUrl` you get whatever layout the browser stored.
`https://app.foxglove.dev` does NOT open in the Simple Browser: it sends `X-Frame-Options: DENY` (the Simple Browser is an iframe) and needs a login.
Over VS Code Remote-SSH: forward ports 8080 and 8765 (Ports panel; both TCP), same URL. From the tailnet: replace `localhost` by the
tailnet IP in all three places (plain http page, so plain `ws://` to any address is allowed), or the Foxglove desktop app on `ws://<tailnet-ip>:8765`.

## The layout: `raptor.json`, generated by `make_layout.py`
Edit `make_layout.py` (stdlib Python), run it, reload the page. Do not hand-edit `raptor.json`.

| Where | Panels (all /drone_1) |
|---|---|
| Status column (always visible) | Mode / armed / FCU link over the last 60 s (`mavros/state`); battery 0-1 (`mavros/battery`); ZED stack health JSON (`zed_stack/status`) |
| Flight tab | 3D following `base_link` (grid, TF, ZED odom arrow green, EKF2 pose arrow blue, ground-truth axes); ZED left (`/compressed`); chase cam; altitude plot (EKF2 / ZED odom / ground truth / ToF, invalid ToF filtered with `{range<40}`); x/y plot EKF2 vs ground truth |
| Camera tab | ZED left (raw); depth 0.3-10 m and confidence, colour-mapped (turbo); optical flow; ZED point cloud (3D, RGB) |
| Debug tab | `/rosout` log; full `mavros/state`; FC IMU acceleration plot; topic graph |

Hidden tabs unsubscribe their topics: the heavy streams (raw left ~47 MB/s, depth, point cloud ~19 MB/s) flow only while the Camera tab is
open. Ground truth (`state/pose`) is in the world frame, EKF2 starts at the takeoff point: the offset between them is the spawn position.

Lichtblick 1.28/1.29 quirks the generator works around (checked 2026-10-13):
- 32FC1 images (ZED depth, confidence) are drawn as grey 0..1 and ignore colormap/min/max. Two user scripts in the layout convert them to
  16UC1 (`/studio_script/depth_mm`, `/studio_script/confidence_u16`), which get the colormap; they run in the browser.
- Indicator and Gauge panels lose their subscription at page load when a 3D or Image panel is mounted (they stay "no data"), so the
  status column uses State Transitions and Raw Messages instead.
- A custom `cameraState` on the point-cloud 3D panel left the cloud out of view; it uses the default camera.

## Debugging: what does the app see?
`scripts/foxglove_probe.py -H <host> -f zed -s /drone_1/zed/zed_node/odom` connects like the app, lists the advertised topics and measures
rate and size of the ones you subscribe to (stdlib, runs on the host). A topic missing there is missing in the app: usually a message
package the bridge container lacks (`docker exec bisg-ros grep "Failed to load schema" /tmp/foxglove.log`; today: `zed_msgs` status
topics and the two `theora` topics).

Bandwidth (measured 2026-10-11, ZED HD720): raw left image 3.6 MB x 16 Hz = 58 MB/s, raw depth the same, point cloud 1.8 MB x 10 Hz =
18 MB/s; `.../left/color/rect/image/compressed` is 194 KiB x 16 Hz = 3 MB/s. Over a remote link use the `/compressed` image topic and
leave the raw depth and cloud for the sim host's LAN.
