# Foxglove web UI and layouts

`./bisg ros start foxglove` (on by default, docker/ros/tools.yaml) starts the bridge (`ws://<host>:8765`, in bisg-ros) and its web UI,
the `lichtblick` compose service (Lichtblick, the open-source Foxglove Studio fork; pinned `LICHTBLICK_TAG`, port `FOXGLOVE_UI_PORT`=8080
in config/bisg.conf). It prints the URL; open it in VS Code with "Simple Browser: Show":

    http://localhost:8080/?ds=foxglove-websocket&ds.url=ws://localhost:8080/ws&layoutUrl=http://localhost:8080/layouts/raptor.json

`ds` connects to the bridge, which the UI's Caddy proxies at `/ws` on the same port (`Caddyfile`), so one port carries everything; `layoutUrl` loads `raptor.json` from this folder (served at `/layouts/`) on every page load and replaces
the stored "raptor" layout, so the repo file always wins. Changes you make in the UI are lost on the next load unless you save them
under another name (Layouts menu) or put them into `make_layout.py`. Without `layoutUrl` you get whatever layout the browser stored.
`https://app.foxglove.dev` does NOT open in the Simple Browser: it sends `X-Frame-Options: DENY` (the Simple Browser is an iframe) and needs a login.
Over a VS Code tunnel or Remote-SSH: forward port **8080** once (Ports panel → Forward a Port → `8080`; VS Code keeps it on reconnect).
VS Code does not forward it by itself (the UI runs in a container, and a URL typed into the Simple Browser is not forwarded): without
it the Simple Browser shows `ERR_CONNECTION_REFUSED`. 8080 is all the page needs since 2026-10-20 (the bridge is proxied at `/ws`). vscode.dev in a web browser does not work (it serves forwarded ports over https, and the
page's `ws://localhost` is then wrong): use VS Code desktop or the tailnet. From the tailnet: replace `localhost` by the tailnet IP in
all three places (plain http page, so plain `ws://` to any address is allowed), or the Foxglove desktop app on `ws://<tailnet-ip>:8765`.

## The layouts: `raptor.json` and `kinetix.json`, generated by `make_layout.py`
Edit `make_layout.py` (stdlib Python), run it, reload the page. Do not hand-edit the JSON. `FOXGLOVE_LAYOUT` (config/bisg.conf, or
`docker/.env` for this machine) picks the layout the printed URL loads and the UI's built-in default; to switch in the browser, change
the file name in `layoutUrl=`. A new layout file needs `docker restart bisg-lichtblick` (the container copies the files at start).

### `kinetix.json`: Kinetix photogrammetry flights
Only the topics Kinetix consumes (its `docs/interfaces.md` §4), so it also replays a Kinetix run bag (`runs/<run>/rosbag/*.mcap`,
Lichtblick "Open local file"). Five user scripts do the arithmetic in the browser:

| Script → topic | What |
|---|---|
| `path_ekf2`, `path_setpoint`, `path_truth` → `/studio_script/path_*` | `nav_msgs/Path` of EKF2, the carrot setpoint Kinetix streams, and the sim truth moved into `map`; a point per 5 cm, restarted at arming |
| `kinetix_track` → `/studio_script/kinetix_track` | distance / height / yaw error to the setpoint, speed (from EKF2 positions), `in_tol` against Kinetix's capture tolerances (0.10 m, 3°, 0.05 m/s; constants in `make_layout.py`, from Kinetix `config/default.yaml`), `settled_s` (Kinetix grabs at 1 s), `setpoint_age_s` |
| `kinetix_flight` → `/studio_script/kinetix_flight` | flight time and distance since arming, EKF2 drift vs truth (3D / horizontal / vertical, max). The map − world offset is measured while disarmed, as Kinetix's `auto_world_to_map`; `offset_from: air` = page opened mid-flight, drift counts from then. NaN without truth (real drone) |

| Where | Panels |
|---|---|
| Status column | mode / armed / FCU link / in-tolerance over 60 s; flight summary |
| Status strip (bottom, thin) | battery; ZED stack health (a camera loss aborts Kinetix) |
| Flight tab | 3D (map grid, the three paths, EKF2 and setpoint arrows, ZED left frustum from `camera_info`); ZED left `/compressed` (what Kinetix captures); chase cam; tracking plot (distance to setpoint, speed = motion blur, height error); drift plot; altitude (EKF2 / setpoint / ToF) |
| Stereo tab | only for Kinetix's stereo comparison modes: left + right raw, depth and confidence (turbo); heavy, flows only while open |
| Debug tab | `/rosout`; `kinetix_track` raw; the setpoint message; full `mavros/state`; left `camera_info` (K) |

Left out on purpose (Kinetix never uses them, ADR-K07): ZED odometry, point cloud, optical flow, FC IMU, topic graph.

### `raptor.json`: the twin

| Where | Panels (all /drone_1) |
|---|---|
| Flight tab | 3D following `base_link` (grid, TF, ZED odom arrow green, EKF2 pose arrow blue, ground-truth axes, the ZED spatial-mapping fused cloud `mapping/fused_cloud` when `spatial_mapping.enabled` in zed.yaml); altitude plot (EKF2 / ZED odom / ground truth / ToF, invalid ToF filtered with `{range<40}`); x/y plot EKF2 vs ground truth |
| Sensors tab | six plots, no 3D: FC IMU acceleration, FC gyro, ZED IMU acceleration, down range (ToF vs flow distance, invalid filtered), PMW3901 flow, barometer. Every plot has its legend in a strip above it (colour, label, current value), not floating over the data |
| Camera tab | the QGC picture's 2x2: ZED left (raw) \| chase cam / depth 0.3-10 m \| depth confidence, both colour-mapped (turbo). The PMW3901 flow is a plot in the Sensors tab |
| Debug tab | `/rosout` log; MAVLink log (PX4 STATUSTEXT, script `mavlink_log`) |
| Graph tab | topic graph, full size. Its settings are not stored in the layout: top-right toolbar, "Topics" diamond → *No topics* gives a node-to-node graph that is far easier to read than the default all-topics view; the arrows button switches top-down / left-right; the rectangle hides services |

Hidden tabs unsubscribe their topics: the heavy streams (raw left ~47 MB/s, depth) flow only while the Camera tab is open (the ZED point
cloud is in the Flight 3D panel, switched off; tick it in the panel's topic list to see it). Ground truth (`state/pose`) is in the world frame, EKF2 starts at the takeoff point: the offset between them is the
spawn position. The MAVLink log shows only what PX4 sends after the page opened (STATUSTEXT is not latched); every earlier line is in
`/rosout` as `FCU: ...`.

Lichtblick 1.28/1.29 quirks the generator works around (checked 2026-10-13, 2026-10-20):
- 32FC1 images (ZED depth, confidence) are drawn as grey 0..1 and ignore colormap/min/max. Two user scripts in the layout convert them to
  16UC1 (`/studio_script/depth_mm`, `/studio_script/confidence_u16`), which get the colormap; they run in the browser.
- Indicator and Gauge panels lose their subscription at page load when a 3D or Image panel is mounted (they stay "no data"), so the
  status column uses State Transitions and Raw Messages instead.
- The latched `/tf_static` reaches only the 3D panels mounted when it arrives: a 3D panel that mounts on a tab switch has no static
  frames and draws nothing (no grid, cloud or poses; this, not the camera, was the "cloud out of view" of 2026-10-13). The script
  `tf_static_repeat` caches `/tf_static` and re-sends the whole set (restamped) with every `/tf` message on
  `/studio_script/tf_static_repeat`; every layout with a 3D panel carries it.
- A user script that returns nothing raises "User Script ... did not produce a message" until its next message, so every script
  returns a message on every input (the last result again when nothing changed).
- Leave the 3D panels' transform **preloading off**, despite the info alert "Transform topics detected ... activating preloading is
  recommended" (one per 3D panel). With a live bridge, preloaded transform subscriptions are dropped on a tab switch: `/tf` stops
  reaching the page and the 3D panels go black (checked 2026-10-20). Preloading is for replaying a bag.
- "Definition of schema 'sensor_msgs/msg/Range' / 'sensor_msgs/NavSatStatus' / 'sensor_msgs/msg/BatteryState' has changed during the
  server's runtime" (errors): Lichtblick 1.29.1 ships the pre-Jazzy definitions of these types and the bridge sends Jazzy's (Range
  gained `variance`, NavSatStatus `STATUS_UNKNOWN`, BatteryState two technology constants). Cosmetic: each topic is decoded with
  its own schema, the plots work. Only a newer Lichtblick (`LICHTBLICK_TAG`, pin change = ADR) can remove it.

## Debugging: what does the app see?
`scripts/foxglove_probe.py -H <host> -f zed -s /drone_1/zed/zed_node/odom` connects like the app, lists the advertised topics and measures
rate and size of the ones you subscribe to (stdlib, runs on the host). A topic missing there is missing in the app: usually a message
package the bridge container lacks (`docker exec bisg-ros grep "Failed to load schema" /tmp/foxglove.log`; today: `zed_msgs` status
topics and the two `theora` topics).

Bandwidth (measured 2026-10-11, ZED HD720): raw left image 3.6 MB x 16 Hz = 58 MB/s, raw depth the same, point cloud 1.8 MB x 10 Hz =
18 MB/s; `.../left/color/rect/image/compressed` is 194 KiB x 16 Hz = 3 MB/s. Over a remote link use the `/compressed` image topic and
leave the raw depth and cloud for the sim host's LAN.
